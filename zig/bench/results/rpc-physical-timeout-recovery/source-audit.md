# Direct generic-VM physical timeout fallback audit

Read-only Source audit. No production/test edits, runtime requests, role/SDK builds or benchmarks. This is separate from the accepted95/95 Root group-retirement snapshot.

## Confirmed direct transport family

Tron provides the strongest exact Source comparison: `rust/main/chains/hyperlane-tron/src/provider/http_client.rs:25,64` explicitly configures a30-second reqwest request timeout. Its configured wallet/solidity endpoints become separate channels (`new:154–171`) under core FallbackProvider. Core `call_provider:179–205` wraps request/probe in its30-second timeout and returns an ordinary error; `call_with_retry_predicate:368–405` then visits the next configured peer. The core fallback timeout→healthy-peer regression is `fallback.rs:830–858`. Tron JSON-RPC also builds EthereumFallbackProvider over every configured RPC URL (`hyperlane-tron/src/utils.rs:37–56`).

Starknet has a custom transport fallback over all configured URLs (`provider/fallback.rs:57–76`), whose `send_request:104–137` continues to the next provider on every HttpTransportError, up to four rounds. MetricProvider uses SDK HttpTransport::new (`metric.rs:61`) without an explicit local per-request timeout in this wrapper. Therefore Source supports fallback after a transport timeout/error, but this audit does NOT claim that a body stalled forever necessarily times out after20 or30 seconds in the Starknet SDK path.

Native direct path: `net/curl.zig:330,460` maps actual curl code28 to RequestDeadlineExceeded. `cloud/http.zig:106–108` preserves it. `net/json_rpc.zig:51–58,88–91` treats that same name as control and returns before trying a healthy second endpoint. Tron wallet and JSON-RPC loops use that same control predicate (`tron/rpc.zig:59–68,87–96`). Main destination Resources are opened with cooperative_reads=false (`relayer_task.destinationOptions/sourceOptions`, Resources.open), so HTTPReplay does not mediate this path. Factory.begin scopes HTTP physicaltimeout to min(physical20s, actualownerClockremaining), while the actual default job budget is120s.

Trigger: configure A and B; only A's relevant read stalls beyond the physical20s limit while actual owner120s budget/cancel remain live, B returns immediately. Native A produces curl28; the generic client exits before B. Endpoint loops always restart at A; there is no preferred-index advancement or failure-aging state in these generic clients. Lane.classify returns retry for this error without rotating generic peers. Repeated direct destination/announcement attempts therefore keep querying A forever while B receives no request. A persisted signed row remains safe but cannot recover normal delivery/proof; even initial direct chain/contract reads may stall construction progress.

Baseline owner independently confirms Aleo's direct REST client has the same isControl early-return family and Rust AllErrors+coreFallback supports timeout→B. Its complete family report is independent; do not infer unverified protocols from the shared HTTP producer alone.

## Routes that must not be conflated

- Cooperative HTTPReplay already maps a completed physical request timeout to UpstreamReadTimeout only while its absolute attempt remains live, before the generic client's control predicate. Main direct resources do not have that Replay.
- Cosmos Tendermint routes through the native EVM Pool, and direct gRPC fallback handles physical RequestDeadlineExceeded as a failed attempt; this is not the same generic isControl branch. Baseline is separately tracing whether the Pool's whole-session20s budget prevents a second peer after a full first-peer timeout. Do not label all Cosmos routes unaffected solely because Pool completion marks retryable.
- Radix Client.call already continues RequestDeadlineExceeded to the next configured read endpoint; only PendingReadIo/OOM/RequestCancelled stop it. No same early-control fallback bypass.
- `Resources.Options.read_attempt_timeout_ms=120000` is a Replay configuration, not actual owner-clock authority for cooperative_reads=false. It cannot justify classifying a direct timeout as ordinary.

## Minimal producer-bound correction proposal (not implemented)

Use the existing precise classification contract from `net/read_replay.zig:100–107`: an actual completed native timeout is ordinary only when physical request budget was strictly smaller than the real owner budget, the owner remains live after completion, and cancel is still false. Owner-clamped/equal budgets, expired owner, injected errors, cancellation, OOM, size errors and other controls keep their original meaning. Existing `UpstreamReadTimeout` already passes generic fallback; do not remove RequestDeadlineExceeded from generic isControl or blindly retry arbitrary errors.

The direct producer is cloud.HttpTransport, because it knows that actual native curl.send returned code28 rather than an injected callback/control. Add an OPTIONAL real monotonic owner budget/deadline authority, bound and restored by the existing Factory.Scope using its Clock.deadline_ns (and analogous actual-owner scopes only where necessary). Immediately before each physical send: check actual absolute budget/cancel, clamp to remaining budget and remember whether ownerlimited; on actual non-injected native deadline completion, normalize only with strict lesser physical budget plus still-live owner/cancel checks. This also prevents refreshing a new full physical timeout at later peers after the absolute deadline. A default/unbound transport must preserve old error provenance, not infer a120s parent from unused config.

No extra Pool, thread, worker, credential owner, request-timeout shortening, RPC business/parser retry policy or SDK rebuild is needed. Ensure any stored deadline state is owned/scoped value, not a borrowed temporary callback pointer. Tests should use real native sockets with shortened fixture-only request budgets to cover A timeout→B healthy, all-bad retry, parent-clamped/equal budget, genuine expired absolute deadline/cancel, injected-control preservation and scope restoration; retain normal configured20s production timeout. Parent approval/disjoint ownership is required before implementation.
