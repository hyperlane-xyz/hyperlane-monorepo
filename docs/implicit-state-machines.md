# Implicit state-machine audit

Base: PR #9959, `8c42d9e643a8a0301f8bdcd8dead2121cd13165a`.

## Scope and interpretation

This is a source audit of the monorepo, not a production-state audit. A state
machine here means a workflow whose next legal action depends on previous
actions: booleans, optional resources, queued work, timers, database rows,
checkpoints, account existence, or transaction ordering. An enum alone does not
make a machine explicit: queue ownership, durable writes, and restart behavior
can still encode transitions elsewhere.

The 133 table entries group implementations sharing one lifecycle; they do not count every
instance of a cache or every chain implementation as a separate machine. Source
searches covered runtime flags, status writes, retry loops, timers, initialization
promises, cursors, persistence, and account mappings. Findings were checked in
their callers and existing tests. Three independent audit workers covered Rust
runtime, TypeScript services, and SDK/CLI; the integrating audit covered infra,
Solidity, and Sealevel programs.

This is an inventory of the machines found, not a proof that every possible
machine has been identified. Generated artifacts, vendored dependency internals,
external services, deployment state, and test-only mock lifecycles are outside
scope. Contract rows describe the important persistent workflows; this PR does
not change contract storage or claim a complete security audit.

## Fixed transitions

The accompanying regression tests exercise interleavings or scheduler behavior,
not just enum values:

- Rebalancer monitor: `Running → Stopping → Stopped` owns the polling loop until
  cleanup completes. A restart during drain is rejected; all stop callers wait
  for the same drain. Startup-handler failure also reaches cleanup.
- TypeScript relayer: `Queued → Retry waiting → Eligible → Relaying`. A queue
  containing only delayed retries yields to the event loop; eligible messages
  behind delayed messages can progress. Each run owns a generation, so old
  sleepers cannot become consumers after a restart; uncached queued work is
  retained. An already-admitted delivery is allowed to settle after stop.
- Rust fallback RPC provider: failure count, priority demotion, and observed
  health are updated against live state under one lock. Concurrent failures
  admitted with one snapshot no longer miss the threshold or restore old health.

- Scraper listener: `Connecting → Ready → Stopped`. Shutdown is terminal;
  listeners acquired after shutdown are immediately released, and startup
  cannot reinstall socket handlers or heartbeat timers. Stop does not wait for
  a blocked connection acquisition to settle.
- Lazy initialization: `Empty → Initializing → Ready` or retryable `Empty`.
  Synchronous throws share the same failure/retry and reset-generation behavior
  as asynchronous rejections.

See the changed tests and the PR validation receipts for executed checks.

### Lander persistence follow-up

`rust/main/lander/src/dispatcher/stages/state.rs:204` (`DispatcherState::store_tx`) logs and swallows transaction, payload-status, and payload-to-transaction mapping write failures. `stages/building_stage/building.rs:96` calls it before forwarding a built transaction to inclusion; therefore the comment “Only send tx ... after we stored it” is not enforced when storage fails. `stages/utils.rs:156` (`update_tx_status`) also always returns success after this helper, allowing inclusion/drop transitions and pool ownership changes to proceed without the durable transition. A crash in this window can recover stale payload state/missing associations and rebuild or replay work. Finalized-success path has its own stricter payload-verdict-first, terminal-commit-last implementation (`finality_stage.rs:363`) and should not be described as affected by the same helper there.

Follow-up should make stage persistence fallible, propagate errors before forwarding/removing work, restore in-memory old status on failure, and add injected failure tests for tx record, payload status, and association writes at build/inclusion/drop boundaries. This is a wider persistence contract change than the isolated RPC-health fix; left explicit rather than partially patched.

### Service follow-ups

These are concrete source traces; fault-injection regressions were not added in this PR.

- **Registry refresh loses invalidation / permits racing publication.** `typescript/http-registry-server/src/services/registryService.ts:98`: read sees dirty, resets LazyAsync, awaits snapshot; watcher marks dirty during the await; completion unconditionally clears dirty. Active watcher then disables time polling, so the newer change can remain unseen until another file event. Also concurrent dirty reads each reset LazyAsync, creating separate refresh promises and allowing late old completion to replace newer cache. Invariant: refresh completion may clear only the invalidation generation it observed; one refresh must own publication. Fix with dirty generation + one refresh owner and gated watcher/fetch tests.
- **Partial RebalancerService initialization is treated as complete.** `typescript/rebalancer/src/core/RebalancerService.ts:143`: contextFactory is assigned before metrics, strategy, tracker, monitor, and orchestrator initialization. If a later await fails, a second public start/executeManual skips initialization because contextFactory exists; callers then use missing pieces. Concurrent initializations can also pass the first check before factory creation resolves. Invariant: publish readiness only once the full component set is initialized, single-flight creation with failed attempts retryable. Needs staged initialization and factory-failure regression tests.
- **Keyfunder timeout leaves writes running.** `typescript/keyfunder/src/core/KeyFunder.ts:85`: Promise.race returns a timeout but does not stop fundChain, which can resume through claim → funding → sweep. In the one-shot CLI this can end before background work finishes; library callers can schedule another cycle while old mutation work remains. Source confirms continuation semantics, but duplicate live funding/production impact was not exercised. Do not blindly retry timed-out writes; require tracked in-flight ownership or explicit cancellation/admission boundaries.

### Infrastructure follow-up: signer failures can escape deployment accounting

`baseDeploy` resolves `multiProvider.getSignerAddress(chain)` before entering its
`runWithTimeout(...).then(...).catch(...)` transition. In concurrent mode,
`Promise.allSettled` then discards this rejection. That chain never receives a
FAILURE status or the settlement callback; `handleExit` can report success based
on the remaining chain statuses. The module-global `deployStatus` and the
post-deploy failure handler also warrant a separate deployment-outcome change.

Concrete next test: reject signer lookup on one chain, succeed another, run both
concurrent and sequential modes, and assert failure accounting, artifact flush,
and nonzero process outcome. Also test SIGINT during INFLIGHT and failed artifact
flush. Fix this as one deployment-result contract rather than changing only the
printed status.
