Aevo xERC20 tokens, which hold a mint authority and a cap for each minter instead of the Standard or Velodrome limits, were supported as `XERC20Type.Aevo`. `deriveXERC20TokenType` returned it for a token, or the EIP-1967 implementation behind it, that carries `updateAuthority`, `setCap`, `authorities` and `caps` and neither the Standard nor the Velodrome setters, and `UnknownXERC20TypeError` still reported any other token.

`xERC20.warpRouteLimits` accepted `{ type: 'aevo', authorized: false }`, for a minter that has no authority, and `{ type: 'aevo', authorized: true, cap }`, where `cap` is `{ type: 'unlimited' }`, for the cap of zero on which the token mints without bound, or `{ type: 'raw', value }`, where `value` is a positive integer that fits a uint256, accepted as a bigint, a safe integer or a decimal string and parsed as a decimal string. A `value` of zero was rejected as not positive, as `{ type: 'unlimited' }` is how a config leaves a minter without a bound, and `warp apply` set a cap of zero for it. The cap the token keeps for a minter whose authority is revoked is not reported, and revoking a minter left it alone, so `warp apply` set the cap along with the authority whenever it authorized a minter, the cap first. A cap bounded what the minter had outstanding, what it had minted and not burned, which the token counted for each minter and lowered with a burn. A raw cap was written to registry files as a quoted string, so a cap above 2^53 read back exactly. `EvmXERC20Module.fromWarpRouteConfig` wrote a raw cap as the decimal string of its value where the config entered the module, so a config the schema did not parse, with a cap spelled with leading zeros, was compared to what the token held as the cap it declared and not as another one. `EvmXERC20Module.update` also compared raw caps by value, so a config handed to it directly did not plan a `setCap` on every apply for a cap the token already held.

`EvmXERC20AevoAdapter.getMintAuthority` took an optional `blockTag` and read the authority and the cap of a minter at that block or, without one, at the latest block as `getBlock('latest')` reported it, instead of each at the latest state of its own. Two such reads could straddle the block that sets the cap of a minter and authorizes it, and pair the cap before it with the authority after it. A read at that block that failed was not made again at the latest state.

The `limits` of `xERC20.extraBridges` rejected Aevo limits, as which other contracts may mint an Aevo token is not modelled, and a non-empty `xERC20.extraBridges` was rejected as a whole when `warpRouteLimits` was Aevo, as nothing was derived for it and Standard or Velodrome limits could not be applied to a token without their setters. The schema rejected Aevo `xERC20.warpRouteLimits` on an `xERC20Lockbox` config as well, as the limits of an Aevo token applied to the router of an `xERC20` route, and the router of a lockbox reads limits through getters an Aevo token does not have. The readers derived what the token holds for a router, `warp check` compared it to the deploy config, and `warp apply` set it with `setCap` and `updateAuthority` on the token. The other minters of an Aevo token, such as the L2 bridge the token authorizes when it is initialized, were neither derived nor managed: `warp check` reported no drift for them and `warp apply` left them alone. A deploy config that omitted `xERC20.warpRouteLimits` for an Aevo route reported the derived limits of its router as drift, as it does for a Standard route.

The owner of an Aevo token was read through its `owner()` and, when `xerc20 apply` expected another owner, handed over with the token's own `setOwner`, in a transaction that follows the limit transactions, as the ownership transfer does for the other token types. `warp deploy` and `warp apply` left the owner of the token alone, as they do for every type. `setOwner` takes effect at once and the new owner accepts nothing, so a transfer to an address that cannot act as owner cannot be undone. The token reverts `setOwner` for the zero address, so an expected owner of the zero address was refused instead of emitting a transaction that fails. `EvmXERC20Reader.readOwner` read no owner only for a token without an `owner()`, such as one that uses AccessControl, and rethrew any other error, for every token type, where it read no owner for any failure, so an owner that could not be read dropped an ownership change without a trace. `EvmXERC20Module.update` with `includeOwnership` refused to hand over an Aevo token whose owner it could not read, and left another type without an `owner()` alone, as before.

`EvmXERC20Module` no longer emitted a transaction for a limit the token already held, a zero limit included. `EvmWarpRouteReader.deriveTokenType` read a HypXERC20 router as `xERC20`, instead of `collateral` or `collateralFiat`, when its token exposed no `mintingCurrentLimitOf`; it recognized the router by the `burn(address,uint256)` call in its code.

`EvmXERC20AevoAdapter`, `AevoXERC20Limits`, `AevoMintAuthority`, `XERC20AevoCapType`, `XERC20AevoCapConfig` and `XERC20_AEVO_ABI` were exported.

`deployAevoXERC20Token` and its result type `DeployedAevoXERC20Token` were exported. They put the recorded Aevo token, its code etched at the addresses it has on the aevo chain, on a Hardhat or Anvil node, the one the provider of the `deployer` is connected to, so that tests of other packages ran against the real token code. They also put a stand-in for the contract the token deposits to when it mints, which accepts the deposit and credits nothing, on the node where its address held no code. A node that kept its state could run them again, and a token another account owned was taken back for the `deployer`, funding that account only when it held too little to pay for it and leaving its balance as it found it.

`XERC20Type`, `XERC20Limits` and the `xERC20.warpRouteLimits` union gained a member, `aevo`, which broke consumers that assumed two. A config literal that declares `type: XERC20Type.Standard` or `type: XERC20Type.Velo` outside a position that fixes its type was widened to the enum and needed a type annotation, such as `XERC20VSLimitConfig`. An exhaustive `switch` over `XERC20Type` or `XERC20Limits` needed an `Aevo` case, and an `else` branch that assumed Velodrome also received Aevo.
