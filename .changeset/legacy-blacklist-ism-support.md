Support was added for Blacklist ISM deployments that predate on-chain enumeration.

- `EvmIsmReader` now probes `blacklistedIds(bytes32)` and `values()` separately, so a deployment without `values()` is derived as a `blacklistIsm` rather than falling through to `testIsm`.
- Enumeration is shared by the reader and `moduleMatchesConfig` through `readBlacklistedIds`, so both reach the same verdict for the same deployment. When `values()` is unavailable, the set is replayed from `MessageBlacklisted` logs via `EvmEventLogsReader`, de-duplicated and sorted; entries are append-only, so the replay is exact. Reading fails when the set cannot be established, rather than yielding a partial one; a deployment that has never blacklisted anything reads as an empty set, which is a result and not a failure.
- Block explorer log queries are now paginated. A single request was issued before, so a response holding the explorer's maximum page of records was indistinguishable from a truncated one and was returned as if complete. Pages are now walked until one comes back short, and a set that cannot be shown to be complete raises an error instead of being returned: when an explorer ignores the `page` parameter, when it refuses to serve a page at all, when a success carries something other than a list of records, or when a query exceeds 20 pages. A failure that cannot be attributed to pagination — a rate limit, a timeout — stays retryable, so the existing retry still applies to it.
- `EvmEventLogsReader`, and `EvmTimelockReader` and `EvmIsmReader` through it, return complete results where a query spanning more than one page was previously truncated in silence. Reading a timelock with more than one page of `CallScheduled`, `CallExecuted`, `Cancelled` or `CallSalt` events is the clearest case. An explorer that cannot paginate is reported as unrecoverable, so these readers fall back to their RPC strategy without retrying first and still return a complete set.
- Every log read served by a block explorer is now reconciled against the chain, `EvmTimelockReader` and `getExtraLockBoxConfigs` included. A page that comes back short proves the explorer has served everything it has indexed, not everything up to the requested block, so the last hour of the range is re-read over RPC and merged, recovering records the explorer had not yet indexed. The hour is converted to a block count from the chain's `blocks.estimateBlockTime`, falling back to a one-second block time where a chain does not publish one, capped so the re-read stays bounded on the fastest chains, and costs at most about twenty extra chunked RPC calls per query — one on Ethereum, four on a two-second chain. An explorer lagging further behind than that window — an hour, or 10,000 blocks where that is shorter, which is roughly forty minutes on the fastest chains — can still under-report.
- `getExtraLockBoxConfigs`, and `EvmWarpRouteReader` through it, now reads its `ConfigurationChanged` logs through `EvmEventLogsReader` rather than calling the block explorer directly, so it gains the same pagination, RPC reconciliation and RPC fallback as every other consumer. An xERC20 with more than one page of those events previously had the excess dropped in silence; on a chain whose explorer serves at most one page, such as zkSync, the read now falls back to the RPC and returns the full set instead.
- `moduleMatchesConfig` no longer throws against a deployment without `values()`; it reads that deployment's entries the same way the reader does, so both reach the same verdict for it. Deriving or checking a Blacklist ISM whose entries cannot be read now fails, naming the chain and address, instead of producing a config that omits them: such a config does not describe the deployment it names. `EvmIsmModule` derives both sides of its comparison, so pinning such a deployment by address fails there too; `moduleMatchesConfig` compares a pinned address directly and is unaffected.
- `EvmIsmModule` redeploys a fresh Blacklist ISM instead of appending in place when the deployed one predates on-chain enumeration, so entries are never appended to a contract that is being phased out.
- Blacklist ISM and Test ISM config checks no longer accept a deployment purely on its module type. A Blacklist ISM config is checked against `blacklistedIds(bytes32)` before its entries are read, and a Test ISM config is confirmed by deriving the deployed module rather than matching any address whose module type is NULL. A deployment that cannot be shown to be one of those two configured types is now reported as a mismatch instead of passing. Checks for other ISM types are unchanged.
- `TestLegacyBlacklistIsm` was added as a test fixture reproducing the pre-audit contract, renamed from `BlacklistIsm` and compiled with a raised `>=0.8.18` pragma for its named mapping parameters; it is otherwise unchanged.
